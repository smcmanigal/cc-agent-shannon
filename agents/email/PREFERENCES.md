# Email Preferences

Learned preferences from Shannon. One per line.

- Auth failures (OAuth token expired or revoked, e.g. after password change, or a bare "Error executing tool" from an email MCP server): try a silent refresh first — `HOME=/workspace/.email-configs/<account> mcp-email-server accounts reauth -a <account>` with no `--force`. That path uses the cached refresh token and needs no browser or device code; confirm it worked with a live read such as `folders list -a <account>`. Only if the silent refresh fails, fall back to the device-code flow: append a reminder to the next routine notice/report sent to Shannon — "ACCOUNT X needs reauth, reply when ready." Don't generate a device code until Shannon signals he's at a browser. When he responds ready, immediately issue a fresh code/link and explicitly call out the ~15-minute code expiry window.

- `Error: command SEARCH illegal in state AUTH` means a WRONG OR NONEXISTENT MAILBOX NAME, not an auth failure. Piped through jq it surfaces as "Invalid numeric literal". Confirm names with `folders list` first. Work folders are "EFX Alerting Emails" (the RTCR/TCI target) and "EFX Reports Output" — singular Report, plural Output; "EFX Report Outputs" is the RULE name, not a folder. The same error also appears INTERMITTENTLY on the work INBOX with a correct name; a 3-try retry loop guarded by `jq -e '.emails'` clears it.

- CLI forms that are easy to get wrong: `emails read -a <acct> <ID> [<ID>...]` takes ids POSITIONALLY — there is no `--id` flag. `emails list --json` returns an OBJECT (`{page, page_size, emails:[...], total}`), not an array; count with `jq '.emails|length'`. An empty mailbox emits a WARNING on stderr that pollutes jq pipes — always `2>/dev/null` plus a `jq -e '.emails'` guard.

- Box-rendered email bodies WRAP long lines, splitting field names across the wrap. `grep -o 'error count: [0-9]*'` returns nothing on TCI alerts because the render breaks it as "transaction count: 25, error \n count: 15". `transaction count` and `error percent` survive the wrap; `error count` does not — use an awk pass over the stripped body instead of a naive grep.

- A watch/list cycle that reports failures retrieved NOTHING; that is not the same as "nothing new". Never append to a seen-ids file on a failed cycle, and run a catch-up as soon as the account is reachable rather than waiting for the next scheduled cycle.

- Hand-written JSONL appends to rule-runs.log can silently lose their closing brace, which kills the whole report aggregation with "jq: parse error: Expected separator between values". Two `type:"note"` lines written 2026-09-17 were truncated this way. Always validate after appending: `while IFS= read -r l; do [ -z "$l" ] || echo "$l" | jq -e . >/dev/null || echo BAD; done < rule-runs.log`. Back the file up before repairing.

- The liveness guard `echo "$out" | jq -e '.emails'` is BROKEN: it EXITS 0 ON EMPTY INPUT, so a command that hung and returned nothing passes as healthy. Confirmed 2026-09-18 (`printf '' | jq -e '.emails'; echo $?` prints 0) after it reported a hung gmail probe as "LIVE total= newest=" — the empty fields were the only tell. Always use `[ -n "$out" ] && echo "$out" | jq -e '.emails|type=="array"' >/dev/null 2>&1`, always pair it with an explicit `timeout`, and treat a LIVE line with an empty total or newest as a failure.

- gmail has ZERO rules, so hourly-run.sh calls its `rules apply` but never opens an IMAP connection — a dead gmail token yields no error, no stderr line and no log entry. Only an explicit probe catches it, and a stale gmail token HANGS (rc=124, no output) instead of erroring. It died four times on 2026-09-18 (detected 16:25, 18:20, 20:24, 21:38 MDT; reauthed 16:28, 18:24, 20:25, 21:40), each silent `accounts reauth -a gmail` working but not holding. The apparent "~2 hour" spacing was probe granularity; the better fit is a ~60-minute Google access-token lifetime with no auto-refresh, i.e. a client-side bug rather than a compromised account. Telegram msg 984 offered Shannon a Google-account security check that this reading would make unnecessary — retract it if the 60-minute pattern holds.

- Container restarts can wipe state files in /workspace/.email-configs (seen 2026-09-22: oceanwide-seen.txt and rule-runs.stderr.log history gone). After any restart, check that seen-ids files still exist before running a watch. If one is missing, rebuild it from the mailbox listing and notify only on genuinely recent items, noting they may be repeats; never re-announce the whole backlog.
